<objective>
Make the suite unable to pass while a required engine is silently absent, and make publication impossible while any gate is red.

Purpose: this is the phase's core deliverable. CI-01 inverts the skip-on-failure pattern for required engines; CI-02 turns "a skipped suite is a passing suite" into a hard failure; CI-08 closes the release path so no artifact can be published from an ungated commit. Together they are the answer to Pitfall 1 ("green CI that verifies nothing").
Output: the `engine_unavailable()` switch wired into all 8 skip sites, a stdlib-only JUnit gate script with its own unit tests, the required-engine CI invocation, and a reusable-workflow release gate.
</objective>

**The tension this plan resolves (D-02):** JUnit XML records counts, not markers. A pure XML gate cannot tell a legitimate optional-engine skip from a required engine silently skipping. Resolution is at the INVOCATION level: the required-engine job runs with `-m "not optional_engine"`, which deselects the 13 optional-engine tests. **Verified:** deselected tests do not appear in the XML at all (a run with `-m "not asyncio"` on `tests/test_pool.py` produced `tests="1"` for 1 passed + 20 deselected). Therefore `skipped > 0` in that job means, by construction, an *unmarked* skip.

**Verified XML shape (pytest 9.1.1):**
`<testsuites name="pytest tests">` containing one or more `<testsuite name="pytest" errors="0" failures="0" skipped="13" tests="19" time="26.699" ...>` elements. Sum `skipped` across ALL `<testsuite>` elements.

**Cost note (measured):** an induced connection failure is slow. Pointing `ENCINO_ORM_POSTGRES_PORT` at a closed port made `tests/test_postgresql.py` take **26.7 s** (vs 1.5 s). `ci.yml`'s `timeout-minutes: 15` has room — do NOT lower it.

**Local verification note:** all six engines run locally today, so a plain local run shows `510 passed, 0 skipped`. The switch and the gate therefore CANNOT be validated locally by simply "not having an engine". Every proof in this plan requires an **induced** failure.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| engine service availability → suite result | A missing service must be an error in CI and a skip locally; the env var is the only switch |
| pytest result → JUnit XML → gate decision | The gate trusts a build artifact; if the artifact is absent or misparsed it must fail closed |
| `tools/ci/check_skips.py` → shell exit code | A gate that exits 0 on a bad input is worse than no gate |
| tag ref → release workflow → PyPI | The publish path is the highest-consequence boundary in the repo |
| reusable workflow call → permissions | A called workflow can only maintain or reduce the caller's permissions |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-03 | Repudiation / Elevation | the switch, the JUnit gate, and both workflows | mitigate | The switch is inverted by an env var supplied only in CI, so a service outage cannot silently degrade to green. The gate runs with `if: always()` so it reports even when pytest already failed, exits non-zero on any `skipped > 0`, and returns 1 (fail-closed) on a missing or unparsable XML rather than raising or exiting 0. `continue-on-error` is forbidden in both files and asserted absent by grep. Every behaviour is proven by an induced failure. |
| T-01-02 | Tampering | `.github/workflows/release.yml` publish path | mitigate | `publish` gains `needs: [ci]` and the `ci` job calls `./.github/workflows/ci.yml` as a reusable workflow, which resolves at the caller's commit — the correct semantics on a tag ref. The rejected alternative (`workflow_run`) would execute against the default branch, not the pushed tag. Proof is a real run against a red gate, not a green one. |
| T-01-09 | Tampering | `ENCINO_ORM_REQUIRE_ENGINES` env var | accept | Anyone who can edit `.github/workflows/ci.yml` can unset the switch and re-enable silent skipping. Accepted: workflow files are protected by branch protection and code review, and the var is deliberately not auto-detected (D-03) precisely because auto-detection is the failure mode being eliminated. The JUnit gate provides a second, independent layer. |
| T-01-04 | Tampering / Supply Chain | `astral-sh/setup-uv@v5` in the release path | mitigate | The `version:` input is pinned in both workflows so the publishing environment runs a known uv. Full action-SHA pinning remains deferred (RESEARCH §Known Threat Patterns) and is recorded as a workflow comment. |
| T-01-10 | Information Disclosure | `PYPI_API_TOKEN` in `release.yml` | accept | Secret handling is deliberately unchanged in Phase 1 — REL-03 (Phase 8) replaces the token with OIDC trusted publishing. Accepted for this phase; the boundary is recorded so it is not lost. |
| T-01-11 | Tampering | `tools/ci/check_skips.py` XML parser | mitigate | `xml.etree.ElementTree` does not resolve external entities by default in CPython, and the input is a trusted build artifact produced by the same job. The parser only reads integer attributes and never interpolates file content into a shell or a path. |

**No package installs occur in this plan**, so no package-legitimacy checkpoint is required here; `tools/ci/check_skips.py` is stdlib-only by design.
