**Measured facts this file must encode (from RESEARCH §Pool Characterization):**

| Invariant | Current behaviour | Phase 4 requirement it precedes |
|-----------|-------------------|---------------------------------|
| Checkout cap | Sequential acquisition respects `max_size`; holding the only connection and acquiring with a timeout raises `PoolExhaustedError` | POOL-02 |
| Overshoot race | With `max_size=2`, 5 concurrent `acquire()` calls yield `_size == 5` — deterministic, reproduced by blocking inside `_create_connection()` | POOL-02 |
| `last_id` scoping | Inside a transaction: read from the held connection. Outside: read from the pool-level `_last_id` cache written by `execute()`, shared across tasks | POOL-03 |
| Release semantics | `release()` only sets `_last_used[db]` and re-queues; it does not commit, roll back, or check liveness | POOL-04 |
| `close()` | Marks disconnected, drains the queue, closes every tracked connection, clears `_connections`/`_last_used`, resets `_size`. Idempotent. **Closes a connection a caller still holds** | POOL-06 |

The race is at `encino_orm/pool.py:114-124`: `get_nowait()` → `QueueEmpty` → `if self._size < self._max_size` → `await self._create_connection()` (an await point) → only then `self._size += 1`. Every concurrent caller passes the cap check before any of them increments.
